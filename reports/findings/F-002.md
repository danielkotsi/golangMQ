# F-002: Data race in consumer bookkeeping — ack/nack racing `dispatchLoop` silently loses acks and stalls delivery

Status: **OPEN** — broker-side, not fixed; blocks suite 3.3 and `go test -race`.

## Finding

The broker's per-consumer state (`inflight`, `inflightTags`,
`pendingMessages`) is mutated from **two goroutines with no shared lock**:

- the queue's `dispatchLoop` goroutine writes it
  (`broker/queue.go:95-97` — `consumer.inflight++`,
  `consumer.inflightTags[tag] = struct{}{}`,
  `consumer.pendingMessages[tag] = msg`), holding `q.mu`; and
- the connection's serving goroutine reads it in `HandleAck`
  (`broker/channel.go:86` — `consumer.inflightTags[tag]`) and reads **and**
  deletes it in `HandleNack` (`broker/channel.go:109-112`) — **holding no lock
  at all**.

`go test -race` reports a genuine `DATA RACE`:

```
WARNING: DATA RACE
Read at ... by goroutine 10:
  GolangRabbitMQBroker/broker.(*Channel).HandleAck()   broker/channel.go:86
  ... route -> routeToChannel -> Connection.Handle -> Connection.Serve
Previous write at ... by goroutine 14:
  GolangRabbitMQBroker/broker.(*Queue).dispatchLoop() broker/queue.go:96
  ... Broker.DeclareQueue -> NewQueue
```

## Observed behaviour

The multi-consumer suite (3.3) — `M` consumers on the **same queue**, each on
its **own** channel — stalls mid-drain. Exact numbers vary between runs because
the outcome depends on race timing:

- `TestMultiConsumer_Distribution` (3 workers × acked drains): got `37/45`,
  `40/45`, `43/45` before a 5s timeout; per-worker counts stay roughly fair
  (`[13 12 12]`, `[15 14 14]`) but a few messages never arrive.
- `TestMultiConsumer_ExactlyOnceAcrossWorkers` (30 messages): got `14`, `23`,
  `26`, `29` of 30.
- Under `-race` the same tests additionally fail the race detector and the
  stall gets *worse* (a racing read may see a consumer that is about to be
  mutated, dropping the ack entirely).

The stall mechanism:

1. A consumer window gets pinned at the prefetch ceiling (default 10).
2. The test acks a delivery; `HandleAck` races with `dispatchLoop` on
   `inflightTags`.
3. When the race "loses", the ack is effectively ignored — `inflight` is
   never decremented for that consumer.
4. `selectConsumer` (queue.go:70-77) then keeps refusing that consumer
   (`inflight < prefetch` fails forever), so the queue stops dispatching to
   it and the test times out waiting for the missing deliveries.

Because the broker iterates `q.consumers` in map order, *which* consumer
wedges — and therefore how many messages are lost — is non-deterministic run
to run. Single-consumer tests (3.4 ack suite) mostly dodge it because there is
only one consumer to wedged, but the race is present there too.

### Escalation (observed during Phase-1 verification)

The race is not a benign stall — under full-suite concurrent load it **aborts
the entire test process**, not just one test:

```
fatal error: concurrent map read and map write

goroutine 118 [running]:
GolangRabbitMQBroker/broker.(*Channel).HandleAck( ... )
        /root/Zone01/golangMQ/broker/channel.go:86   +0x19f
GolangRabbitMQBroker/broker.(*Channel).route( ... )
        /root/Zone01/golangMQ/broker/channel.go:29
GolangRabbitMQBroker/broker.(*Connection).routeToChannel( ... )
        /root/Zone01/golangMQ/broker/connection.go:145
GolangRabbitMQBroker/broker.(*Connection).Handle( ... )
        /root/Zone01/golangMQ/broker/connection.go:131
```

In a run of the full Phase-1 suite (`go test ./tests/ -count=1`,
`-run Test(Ack|Nack|MultiProducer|Channel|Disconnect|Publish|Routing)` with the
multi-consumer guards excluded), roughly **one in two runs** crashes this way.
Because a Go map hit by a concurrent read+write is *fatal*, the whole broker
goroutine panics and the test binary dies — a passing test such as
`TestAck_FreesPrefetchSlot` can be killed mid-run by an unrelated channel's
race. `go test -race` flags the same access deterministically.

This means **no subset of the suite can be considered stable** until F-002 is
fixed: the "single-consumer dodge" is timing luck, not correctness.

## Why that behaviour

`Channel.HandleAck`/`HandleNack` run on **one** goroutine
(`Connection.Serve` → `routeToChannel` → `Channel.route`) while *every queue's*
`dispatchLoop` runs on **a different** goroutine spawned by `NewQueue`. Both
paths reach the same `Consumer` maps:

- the acks/nacks path finds the consumer by scanning `ch.consumers` and then
  touches `consumer.inflightTags` / `consumer.pendingMessages` /
  `consumer.inflight`;
- the dispatch path touches exactly those fields while selecting and marking
  each delivery.

The only mutex in the broker that serialises message state is `q.mu`, and the
ack/nack path **never takes it** (`HandleAck` does not lock; `HandleNack` does
not lock before deleting from the maps; `Broker.Ack` locks `q.mu` only inside
the queue, but the *scan of `ch.consumers` + the map read* happens before that
lock is reached, and `HandleNack`'s deletes happen with no lock at all).

So two unsynchronised goroutines concurrently perform a lookup/delete and an
insert on the same maps. In Go, a concurrent map read/write is a data race; the
observed symptom is that ack handling races and sometimes "wins" by reading a
stale tag and bailing out with the `if _, ok := ...; ok` check failing, so
`broker.Ack` is never invoked and `inflight` never returns to below prefetch.

## Why it needs to change

1. **Data race (UB).** Go explicitly forbids concurrent map access; `-race`
   flags it and it can panic or corrupt state on real deployments, not just in
   tests.
2. **Silent message loss.** Once a consumer wedges at its prefetch ceiling,
   queued messages stop being delivered to it with no error anywhere — the
   queue's un-dispatched backlog just sits there. This breaks the "exactly
   once across M workers" guarantee that suite 3.3 is specified to claim.
3. **Non-determinism.** With more than one consumer on a queue, correct,
   race-free behaviour is impossible to observe or verify; quantities and even
   which deliveries arrive change run-to-run.
4. **`go test -race ./tests/` can never pass** until this is fixed, so the
   Phase-1 definition of done (§4) is blocked by it.

## How it needs to be countered

Give the consumer bookkeeping a single owner. Any of these closes the race:

- **Option A (minimal):** make `HandleAck`/`HandleNack` take `q.mu` around
  their scan of `ch.consumers` and their map mutations. `dispatchLoop` already
  holds `q.mu` when it mutates the same maps, so this turns ack/nack mutation
  into the same critical section. Care: `HandleNack` must not deadlock if the
  requeue (`Broker.Enqueue`) re-locks `q.mu` — the requeue path inside the
  broker currently deals in raw messages and would need to be sequenced after
  the maps are consistent.
- **Option B (recommended):** give each `Consumer` its own `sync.Mutex`
  guarding `inflight`, `inflightTags`, `pendingMessages`. Both `dispatchLoop`
  and ack/nack lock `consumer.mu` (not `q.mu`) around any touch of these
  fields; `selectConsumer` briefly snaps the counters under a short lock. This
  narrows the critical section, keeps `q.mu` for queue-level invariants, and
  is unaffected by requeue/re-dispatch.
- **Option C (architectural):** move ack/nack into the queue-goroutine model —
  make `dispatchLoop` the only writer and have `HandleAck`/`HandleNack`
  enqueue an ack/nack event onto the queue's channel rather than mutating
  consumer maps directly. Cleanest long-term, largest change.

### Recommendation

Adopt **Option B**. It is a contained change (one mutex per consumer + two
call-site updates), removes the race entirely, and keeps the existing
queue-vs-channel separation intact. Option A is acceptable as an emergency
fix but risks lock-ordering subtleties around requeue.

## Scope

- **Repro:** `go test -race ./tests/ -run TestMultiConsumer_Distribution
  -count=1` (race + stall); also `TestMultiConsumer_ExactlyOnceAcrossWorkers`.
- **Status:** **OPEN** — broker-side, not fixed; no black-box workaround
  exists. The affected tests are blocked until the broker changes (per the
  Phase-1 plan, production broker code is not modified here).
- **Files touching the race:** `broker/queue.go` (`dispatchLoop`,
  `selectConsumer`), `broker/channel.go` (`HandleAck`, `HandleNack`),
  `broker/broker.go` (`Ack`/`Nack` glue).
- **Tests exercising it:** `tests/multiconsumer_test.go` (3.3) currently
  intended-to-pass but awaiting the broker fix.
