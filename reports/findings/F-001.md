# F-001: Channels silently overwrite consumers — one consumer per channel is enforced by accident, not by design

Status: **PARTIAL** — test-side resolved; broker-side guard not implemented.

## Finding

The broker is designed around the assumption that **a channel carries at most
one active consumer**, but nothing in the code enforces that rule. When a
client registers a second consumer on an already-consuming channel, the first
consumer is silently overwritten instead of an error being returned (or the
second consumer being accepted).

## Observed behaviour

While writing `TestNack_DeadLetter` (dead-letter routing), the test declared a
main queue and a dead-letter queue, then invoked `Consume` twice on the same
channel:

```go
ch.Consume("mainq", ctx)   // consumer for mainq
ch.Consume("dlq", ctx)     // consumer for dlq (same channel)
```

Result: after publishing and nacking `requeue=false`, the dead-lettered
message never arrived on the DLQ. A white-box probe of the broker state showed:

```
consumers registered: 1
tag=""
```

Both `Consume` calls succeeded at the protocol level (`basic.consume-ok` came
back), so the client believed there were two consumers. In reality the channel
held only one.

A separate-channel version of the exact same scenario passes cleanly, which is
why the failure is tied to *same-channel* consumption, not to dead-lettering
itself.

## Why that behaviour

The channel stores its consumers in a map keyed by consumer tag:

```go
type Channel struct {
    ...
    consumers map[string]*Consumer
}
```

and registration is a plain map write:

```go
func (b *Broker) RegisterConsumer(consumetTag, queue string, ch *Channel) error {
    c := NewConsumer(consumetTag, q, ch)
    q.registerConsumer(c)
    ch.consumers[consumetTag] = c
    return nil
}
```

The SDK's `Consume` does not send a consumer tag (the `ConsumerTag` field of
`protocol.Consume` is empty), and `NewConsumer` auto-generates a tag only for
its own bookkeeping:

```go
func NewConsumer(tag string, queue *Queue, ch *Channel) *Consumer {
    if tag == "" {
        tag = fmt.Sprintf("ch.%d.consumer.%d", ch.id, len(ch.consumers)+1)
    }
    ...
}
```

The auto-generated tag is **not written back** into `ch.consumers` — the map is
still keyed by the original `consumetTag` value, which is `""` for every
consumer the SDK creates. The second `Consume` therefore overwrites the first
under the same empty-string key:

```
consumers[""] = consumerOf(mainq)   // first consume
consumers[""] = consumerOf(dlq)     // second consume replaces the first
```

The queue was correctly registered on both queues (`mainq.consumers` and
`dlq.consumers` still reference their own consumers), which is why the broker
state looks plausible. But the *channel* only knows about the newest consumer,
and per-channel lookups (dispatch of acks/nacks via `HandleAck` /
`HandleNack`, which iterate `ch.consumers`) only ever see the last one.

## Why it needs to change

1. **Silent data-loss risk.** A client that legitimately wants two consumers
   (e.g. a dead-letter consumer as in the failing test) gets one silently
   dropped. Dead-lettered messages are then never delivered, and there is no
   error or warning to explain why.
2. **Acks/nacks can be misrouted.** Because `HandleAck`/`HandleNack` look for
   the pending delivery tag by walking `ch.consumers`, losing a consumer means
   its in-flight messages become unreachable — acks for them are ignored, and
   nacks of the *other* queue's messages can be applied to the wrong consumer
   or dropped entirely. `TestNack_DeadLetter` demonstrated the dropped-nack
   variant: the nack was accepted, the publish was fire-and-forget, and the
   message just vanished from the system.
3. **The invariant is unstated.** The whole design (per-channel consumer
   runtime, prefetch accounting on `Consumer`, `dispatchLoop` selecting from
   `q.consumers`) assumes one consumer per channel. Since the invariant is not
   expressed anywhere, users and tests can trip over it without any hint.
4. **Same-channel fan-in into one `ch.Incoming`.** Even if multi-consumer
   registration worked, the SDK funnels every consumer's deliveries into the
   channel's single `Incoming` slice-valued channel, so a client could not
   tell which queue a delivery came from without inspecting
   `Deliver.Exchange`.

## How it needs to be countered

Two mutually exclusive directions; pick one and make it explicit in the
protocol and in code.

### Option A — Enforce one consumer per channel (aligns with the current design)

Restrict the protocol so a second `basic.consume` on a channel that already has
an active consumer is rejected explicitly.

- `HandleConsume` must detect `len(ch.consumers) > 0` (or `!ok` on
  `ch.consumers[""]`) before registering, and reply with an `error` envelope
  instead of `basic.consume-ok`, e.g.:
  `"channel already has a consumer"` — this is the upstream (canonical) error
  surface the SDK already understands.
- The SDK's `Consume` must surface that error to the caller (it already does
  via request/response matching on `error` envelopes).
- This is the smallest change, requires no protocol additions, and turns the
  current accidental behaviour into a safe, documented error.
- Consequence for users: a library wanting a DLQ consumer must open a second
  channel — exactly what the corrected `TestNack_DeadLetter` does.

### Option B — Support multiple consumers per channel (larger change)

If multiple queues per channel is a desired feature, the broker must be
extended properly rather than accidentally:

1. **Require unique consumer tags** end-to-end: the SDK must send a
   `consumer_tag`, the broker must validate it (reject duplicates with an
   error), and `NewConsumer` must store the returned `ch.consumers[tag]`.
2. **Return the consumer tag** in `basic.consume-ok` (the payload already has
   a `ConsumerTag` field), so the client can correlate deliveries to
   consumers.
3. **Make channel-level delivery fan-in explicit**: either the SDK routes
   `basic.deliver` envelopes to distinct per-consumer channels, or the client
   must filter `Deliver.Exchange`/`RoutingKey` on the single `Incoming`.
4. **Correct ack/nack routing** stays per-consumer (it already is — keys by
   delivery tag inside each consumer), so this part works as long as the
   consumers are actually *present* in `ch.consumers`.

### Recommendation

Adopt **Option A** now. It matches the broker's intended design, is a one-spot
broker change plus an SDK error-propagation check, and prevents the silent
overwrite/data-loss class of bugs. Revisit Option B only if multiple
consumers per channel becomes a product requirement.

## Scope

- **Repro:** two `Consume` calls on one channel — one per queue — with
  `Nack(requeue=false)` on the first delivery; the second consumer's
  dead-letter delivery never arrives.
- **Status:** test-side resolved (`TestNack_DeadLetter` now uses separate
  channels for main and DLQ consumers); broker-side guard not yet
  implemented.
- **Regression guard:** `tests/finding_f001_test.go`
  (`TestFindingF001_SecondConsumeOnSameChannel`) intentionally fails on the
  current broker; passes once Option A or B lands.
- **Files touched by tests:** `tests/ack_test.go` (separate `dlqCh`),
  diagnostic tests `broker/zdiag_test.go`, `tests/diag_dlx_test.go`,
