# Changes for F-002 — fixing the consumer-bookkeeping data race (`fix/finding-002`)

What changed on this branch to resolve `reports/findings/F-002.md`, relative to
its parent `dkotsi/integrationTests`.

## 1. Problem recap

F-002: the broker's per-consumer state (`inflight`, `inflightTags`,
`pendingMessages`) was mutated from two goroutines with no shared lock:

- the queue's `dispatchLoop` goroutine wrote it holding `q.mu`
  (`broker/queue.go`)
- the connection's serving goroutine read/mutated it in `HandleAck` /
  `HandleNack` and in `Broker.Ack` **without taking any consumer lock**

`go test -race` flagged a genuine data race; at full-suite concurrency the
concurrent map read/write escalated to `fatal error: concurrent map read and
map write`, killing the whole test process. The multi-consumer suite
(`TestMultiConsumer_ExactlyOnceAcrossWorkers`, `TestMultiConsumer_Distribution`)
stalled mid-drain and could never pass.

## 2. Production change — per-consumer mutex (finding's recommended Option B)

Every consumer now owns its bookkeeping: a single `sync.Mutex` guards
`inflight`, `inflightTags`, and `pendingMessages`, and **all** touch-points
lock it. This gives the bookkeeping a single owner and removes the race without
changing queue-level invariants.

| File | Change |
|------|--------|
| `broker/consumer.go` | Added `mu sync.Mutex` to `Consumer`. |
| `broker/queue.go` `selectConsumer` | Snaps `c.inflight < c.prefetch` under `c.mu` before choosing a consumer. |
| `broker/queue.go` `dispatchLoop` | Marks a delivery (`inflight++`, `inflightTags`, `pendingMessages`) under `consumer.mu`; the write-error re-enqueue path unmarks the same fields under `consumer.mu`. |
| `broker/queue.go` `unregisterConsumer` | Re-enqueues a consumer's `pendingMessages` and resets its maps/counter under `c.mu`. |
| `broker/channel.go` `HandleAck` | Looks up the delivery tag in `consumer.inflightTags` under `consumer.mu` before delegating to `Broker.Ack`. |
| `broker/channel.go` `HandleNack` | Reads `pendingMessages` and does the delete/`inflight--` under `consumer.mu`; **releases `consumer.mu` before** taking `consumer.queue.mu` for the requeue or DLX publish. |
| `broker/broker.go` `Ack` | Scans `q.consumers` and performs the tag removal/`inflight--` under `c.mu` (while holding `q.mu`). |

### Lock ordering — why there is no deadlock

- Queue-level paths always acquire in the order **`q.mu` → `consumer.mu`**
  (`dispatchLoop`, `Broker.Ack`, `unregisterConsumer`, `selectConsumer`).
- Ack/nack paths acquire `consumer.mu` alone and **never hold it while
  acquiring `q.mu`**: `HandleNack` copies the message and clears the maps under
  `consumer.mu`, then unlocks, and only then takes `queue.mu` to requeue.

So no goroutine ever waits for `q.mu` while holding `consumer.mu` (and only one
goroutine can hold `q.mu`), which rules out an ABBA lock cycle.

## 3. Test-harness change — multi-consumer drain (`tests/`)

The two multi-consumer tests were also failing for a reason *separate from the
race*, discovered while verifying the fix: the drain loop read workers in
strict round-robin with a fresh 5s timeout per worker. Because the broker hands
messages out unevenly (queue selection order is map-iteration order), any time a
worker's `Incoming` ran dry before the shared queue was drained, the loop
blocked 5s on that empty worker and the test timed out — even though the
remaining deliveries were sitting unread in another worker's buffer. Tracing
confirmed the broker delivered 30/30 and the client's read loop consumed 30/30,
while the test stalled at 23.

| File | Change |
|------|--------|
| `tests/helpers.go` | Added `mergeWorkerDeliveries(chs ...*gomqSDK.ClientChannel) <-chan workerDelivery`. One goroutine fans each worker's `Incoming` into a single stream, tagging each delivery with its source channel (so acks still go out on the correct worker channel); the stream closes when every source has closed. |
| `tests/multiconsumer_test.go` | Both `TestMultiConsumer_ExactlyOnceAcrossWorkers` and `TestMultiConsumer_Distribution` now drain through the merged stream instead of round-robin; `Distribution` maps each channel to its worker index for per-worker counts. |

The tests keep their intent — exactly-once across workers (multiset equality,
no dupes/loss) and >1 active worker — and still fail on a genuinely wedged
broker (the 5s timeout fires only when *nothing* arrives anywhere).

## 4. What was deliberately not changed

- **F-001** (`TestFindingF001_SecondConsumeOnSameChannel`) stays red by design —
  different finding, out of scope.
- No protocol/SDK changes; no new dependencies; `go.mod`/`go.sum` untouched.
- Delivery-tag wraparound, non-deterministic `selectConsumer` order, and
  missing heartbeats remain deferred (latent, logged in the finding's scope).
