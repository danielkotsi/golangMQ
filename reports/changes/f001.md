# F-001 changes — multiple consumers per channel

What has been changed on the `fix/finding-001` branch, relative to the state it
inherited from `dkotsi/integrationTests`.

## Finding addressed

**F-001** (`reports/findings/F-001.md`): a channel stored its consumers in a map
keyed by the consumer tag **as sent by the client**, which is empty for every
consumer the SDK creates. The auto-generated tag computed in `NewConsumer` was
never written back into `ch.consumers`, so a second `basic.consume` on an
already-consuming channel overwrote the first consumer under the empty-string
key — silently dropping the first consumer.

Resolution: **Option B** (support multiple consumers per channel), so a client
may legitimately register more than one consumer on the same channel.

## Production code — `broker/`

### `broker/broker.go`
- `RegisterConsumer` now keys `ch.consumers` by the consumer's **actual
  (possibly auto-generated) tag** (`c.tag`) instead of the raw `consumetTag`
  argument. Each consumer therefore gets a unique entry in the channel map and
  none is silently overwritten.
- `RegisterConsumer` signature changed to return `(string, error)` so callers
  can learn the resolved consumer tag and receive registration errors.
- Duplicate consumer tags are rejected with an error instead of silently
  replacing the existing consumer: `"consumer tag %q already in use on channel
  %d"`. Auto-generated tags (`ch.<id>.consumer.<n>`) never collide, so this
  only guards against clients that send an explicit tag twice.

### `broker/channel.go`
- `HandleConsume` propagates registration errors to the client via the `error`
  envelope (channel-level counterpart of the existing error path) before
  writing `basic.consume-ok`.
- `basic.consume-ok` now returns the **resolved consumer tag** (the
  auto-generated one when the client sent none) instead of echoing back the
  empty request tag, so the client can correlate deliveries with consumers.

With both consumers present in `ch.consumers`, per-channel lookups used for ack/
nack routing (`HandleAck` / `HandleNack`) still find the first consumer's
in-flight deliveries, so nacks/acks on it are handled correctly.

## Regression guard

- `tests/finding_f001_test.go` (`TestFindingF001_SecondConsumeOnSameChannel`)
  now passes via the Option B path: the second consume on a channel is
  accepted, and a `nack(requeue=true)` on the first consumer's delivery is
  handled and redelivered end to end. When F-001 was present the nack was a
  silent no-op and no redelivery ever arrived.
