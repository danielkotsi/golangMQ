# F-004 changes — multiple consumers per channel, end to end

What has been changed on the `feature/MultipleConsumersPerChannel` branch,
relative to the state it inherited from `dkotsi/integrationTests`.

## Finding addressed

**F-004** (`reports/findings/F-004.md`): the F-001 broker-side fix made the
*bookkeeping* support multiple consumers per channel, but the feature was **not
usable end to end** — the wire protocol discarded the consumer's identity:

1. `protocol.Deliver` (here **and** in the SDK) had no `consumer_tag` field.
   `dispatchLoop` picked a specific consumer internally and then wrote an
   envelope that omitted which consumer it selected.
2. The SDK's `Consume` returned the channel's single shared `ch.Incoming`
   regardless of which consumer was registered; it never even read the
   `ConsumerTag` the broker echoed in `basic.consume-ok`.
3. The SDK's `route` funneled **every** `basic.deliver` on the channel into that
   same `ch.Incoming`, so deliveries from all queues a channel consumed were
   merged and indistinguishable.

So two legitimately-registered consumers on one channel still received a merged
stream; per-consumer receive, cancel, or correlation was impossible.

Resolution: carry the recipient consumer's tag on `basic.deliver` (broker
protocol + broker dispatch), and route client-side into per-consumer channels
(SDK v0.3.2), with an explicit fallback to the legacy `Incoming` when the tag is
absent. The feature activates only when **both** sides are new; mixed-version
mixtures degrade gracefully (compat matrix below).

## Production code — `broker/` + `protocol/`

| File | Change |
|------|--------|
| `protocol/events.go` | Added `ConsumerTag string \`json:"consumer_tag,omitempty"\`` to `Deliver`. Additive; `omitempty` keeps legacy envelopes well-formed. |
| `broker/queue.go` `dispatchLoop` | Stamps `ConsumerTag: consumer.tag` on the `Deliver` it writes (the consumer is already selected at dispatch time). |

Nothing else was needed broker-side: `RegisterConsumer` / `HandleConsume` already
store and echo the resolved tag (F-001), and acks/nacks already route per
consumer by delivery tag (F-002).

### Cross-repo dependency — SDK v0.3.2

`go.mod` / `go.sum` bump `github.com/danielkotsi/golangMQSDK` **v0.2.0 → v0.3.2**
(published; no `replace`). The matching SDK change (in the other repo) is:

- `Consume` sends a **client-authoritative consumer tag** and **pre-registers
  the per-consumer channel** under that tag *before* sending `basic.consume`,
  cleaning it up on every failure path. The entry therefore exists before the
  first `basic.deliver` can arrive, closing the race where a pre-queued
  delivery arrived before `basic.consume-ok` and fell back to `Incoming`
  (F-004.1 — see `reports/findings/F-004.1.md`).
- `route` looks the entry up by `deliver.ConsumerTag` and forwards deliveries
  to it, falling back to the legacy `Incoming` when the tag is absent (old
  broker / unknown tag). `Consume` falls back to `Incoming` when the broker
  echoes an empty tag, exactly like v0.2.0.
- `client.go`: `Client.Close` now stops `readLoop` before closing delivery
  channels (removing a send-on-closed-channel panic race with concurrent
  Close + inbound delivery), plus fixes the OpenChannel nil-pointer panic on
  context timeout; `handleChannelCloseOK` resolves the pending request with a
  `"channel closed"` error instead of `nil`.

Two **contract notes** that come with v0.3.2 (flagged so they are reviewed
consciously before merge):

- A client-initiated `ClientChannel.Close()` now returns a non-nil
  `"channel closed"` error when the broker replies with `channel.close-ok`
  (F-003's response path), rather than `nil`. The broker repo's
  `TestChannel_CloseRequeuesUnacked` was updated to assert Close resolves
  promptly on the response path (not the context deadline) without pinning the
  error value.
- The per-consumer path keys on the **broker-echoed** tag; the current broker
  never normalises tags (it only auto-generates when the client sends none),
  so echo == client tag.

### New F-004 regression tests — `tests/finding_f004_test.go`

| Test | Guards |
|------|--------|
| `TestFindingF004_ConsumeReturnsDistinctChannels` | Two `Consume` calls on one channel return **distinct** chans (`chanA != chanB`), and each delivers its own message. |
| `TestFindingF004_DeliveriesRoutedToCorrectConsumer` | N messages to Qa/Qb on one channel arrive **only** on their consumer's chan — fan-in is explicit, no leakage. |
| `TestFindingF004_ConsumerTagStampedPerConsumer` | Every delivery carries a non-empty `ConsumerTag`; the tag is **stable per consumer** and **distinct across the two consumers** on one channel. |
| `TestFindingF004_NackRedeliversOnSameConsumer` | A `nack(requeue=true)` on consumer A's delivery redelivers **only** on A's chan (the requeue goes to the front of A's queue), never onto B's chan, preserving delivery tag and consumer tag. |
| `TestFindingF004_CloseClosesPerConsumerChans` | Closing the client closes **every** per-consumer chan **and** the legacy `Incoming` exactly once, so blocked consumers unblock. |

## Compatibility matrix (v0.3.2 behaviour vs wire tag)

| Broker | SDK | `basic.deliver` carries tag? | Behaviour |
|--------|-----|------------------------------|-----------|
| old | old | no | shared `Incoming`; single consumer per channel effectively enforced (F-001) |
| new | old | yes (ignored) | shared `Incoming`; multiple consumers registered but indistinguishable |
| old | new (v0.3.2) | no | tag `""` → not found → falls back to `Incoming`; behaviour unchanged |
| new | new (v0.3.2) | yes | **per-consumer chans; feature fully on** |

The feature activates only when both sides are new; the fallback guarantees no
regression for any intermediate mixture.

## Sub-finding discovered during the PR — F-004.1

The first v0.3.1 cut of the SDK created the per-consumer entry in `route` on
`basic.consume-ok`. Because the broker's `dispatchLoop` is a separate goroutine,
`basic.deliver` can arrive **before** `basic.consume-ok`; the entry then did not
exist yet and pre-queued messages silently fell back to `Incoming`
(`TestMultiProducer_NoConsumerThenAttach` flaked 1-in-~30 under `-race`). Fixed
in v0.3.2 by pre-registering the entry in `Consume` before sending the request.
Full write-up: `reports/findings/F-004.1.md`.

## Deliberately not changed (deferred, per the finding)

- **Delivery-tag ambiguity across queues on one channel** — delivery tags are
  allocated per queue, so two consumers on different queues can hold the same tag
  number simultaneously; `HandleAck`/`HandleNack` match by delivery tag alone.
  Unreachable before this feature; follow-up options include consumer tag in
  `basic.ack`/`basic.nack` or globally-unique tags.
- **Removing the unused broker-side `Consumer.ch`** — dead field, cleanup task.
- **Backpressure / slow-consumer policy, client-settable prefetch** — separate
  perf/protocol features.
- F-002's race fix and F-003's `channel.close-ok` are already on the inherited
  `dkotsi/integrationTests` base and are unchanged here.
