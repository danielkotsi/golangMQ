# F-003 changes — broker replies `channel.close-ok`

What has been changed on the `fix/finding-003` branch, relative to the state it
inherited from `dkotsi/integrationTests`.

## Finding addressed

**F-003** (`reports/findings/F-003.md`): when a client sent `channel.close`,
the broker ran the teardown (deleted the channel from the connection map,
called `ch.cleanup()` to unregister its consumers) but never replied with
`channel.close-ok`. The request/response method therefore never completed: the
SDK registers `handleChannelCloseOK` in the read loop and `ClientChannel.Close`
waits on the response channel, but only the client-side context deadline ever
unblocked it — a protocol violation on every channel close. Missing close-ok
also meant the SDK's `handleChannelCloseOK` (which deletes the channel from the
client map and closes the channel's `Incoming`) never ran, leaving a stale
channel entry and an open `Incoming` channel client-side.

Resolution: the broker acknowledges `channel.close` with `channel.close-ok`,
mirroring the existing `channel.open-ok` reply in `ChannelOpen`. No SDK change
was needed — the full handshake is already implemented client-side.

## Production code

### `broker/connection.go`
- `Connection.ChannelClose` now sends the acknowledgment after teardown:
  `c.WriteEnvelope(id, protocol.ChannelCloseOKType, env.RequestID,
  protocol.ChannelCloseOK{ID: id})`. It is written **after** `ch.cleanup()` so
  the client's `handleChannelCloseOK` runs once teardown is linearised.

### `protocol/events.go`
- Added the `ChannelCloseOK` struct (`ID uint16 `json:"id"``), referenced by the
  SDK's `handleChannelCloseOK` but missing from the broker's protocol package.
  The `ChannelCloseOKType` method constant already existed.

## Regression guard

- `tests/channel_test.go` (`TestChannel_CloseRequeuesUnacked`) previously
  tolerated `ClientChannel.Close(ctx)` returning `ctx.Err()` after a 700 ms
  context (the F-003 symptom); it now asserts `ch.Close(ctx)` returns nil.
  Close resolves on the response path well within the deadline, and the
  requeue of unacked deliveries is asserted as before.
- `TestChannel_MultipleChannelsOverOneConnection` still passes (the two-suite
  channel test stays green).
